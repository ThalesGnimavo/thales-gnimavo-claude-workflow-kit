# Chapter 7 — A day with the kit

## Lesson

Morning, ten minutes. Open the terminal in this folder, type `claude`, then `/day`.
Read each project's one screen. Decide one thing: which project, one session or several.
Then `/next <project>`, from this same folder. The session starts from the queued prompt. Say "go" or
correct the prompt first. Then leave.

During the day, do not watch. You send three kinds of messages only: a decision when
Claude stopped on a level-1 question, an unblock when it lacks something only you have,
a correction when you read something wrong. Everything else waits for the evening.

Evening, fifteen minutes. Read the session log, not the conversation. Demand the raw
output for anything marked done. Read "Decisions taken without the user" and veto what you
dislike. Check that the next prompt names one slice a fresh session could start alone.
Read `casp check`: PASS per rule, or a FAIL with the reason. Then close the terminal.

What never gets delegated: what the project is for, what comes first, anything that
spends money, anything that goes out to another person, anything judged on a real device
or in a real room.

Three mistakes everyone makes in the first week:

1. Asking for everything at once. The answer is long, vague and unverifiable. One slice.
2. Trusting "done". Ask for the output. Every time.
3. Letting the session run for hours. Memory fills, quality drops. Close, then open a new one.

The method is not about Claude being clever. It is about the state being written down,
checked, and handed over. How it was arrived at is told on the author's blog, linked in
`README.md`.

## What a good answer contains

- A project name, a slice small enough for one sitting, a level-1 question that is
  plausible for that slice.
- If the slice is too large ("write the whole business plan"), say so and ask for the
  first piece of it.
- After this chapter, propose `/new-project` with the slice as its first prompt.
